# Specificity and Resource-Fit Policy

Use this policy to keep an atlas decision-useful, compact, and matched to the
user rather than turning it into a generic course outline.

## Answer-first contract

The first useful section after the confirmed brief must answer the user's real
question. It must contain:

1. a direct bottom line;
2. the few points that change what the user should do or understand;
3. concrete recommendations or representative options;
4. the important trade-offs or conditions attached to them.

Do not make the user read definitions, methodology, disclaimers, or a source
plan before seeing the answer. Background belongs after the direct answer.

## Specificity gate

Use proper nouns and exact objects whenever the topic permits them:

- products, tools, platforms, applications, institutions, standards, datasets,
  companies, people, accounts, books, channels, papers, and communities;
- current segments, major approaches, representative players, or canonical
  examples;
- exact chapters, videos, pages, episodes, workflows, commands, exercises, or
  decision rules.

For every named recommendation, state why it is relevant, who or what it fits,
and the decisive limitation. A disclaimer is not a substitute for analysis.

Do not hide all specific options merely because a topic is high-stakes. When
the user requests decision support, obtain the variables that materially alter
the recommendation, use current evidence, state the date and assumptions, and
give conditional or scenario-based options. Never imply a license, fiduciary
relationship, diagnosis, guaranteed outcome, or certainty that the evidence
does not support.

## Internal coverage, compact presentation

Map the field as it exists for this user's goal, not only as a textbook
taxonomy. Depending on the topic, include the relevant mix of:

- major segments or schools;
- leading or representative products, organizations, people, works, tools, or
  methods;
- what each is known for;
- how the options differ;
- current status or recency;
- a selection rule the user can apply.

For fast-changing, commercial, industry, current-event, or high-stakes topics,
date-stamp the field guide and verify current names, availability, and status.
For stable or historical topics, interpret "current" as the present state of
scholarship, access, or practice.

The field map, practical setup, and conceptual dependencies are research
checks, not mandatory standalone chapters. Synthesize only the useful parts
into a small number of named subsections under one core guide. Do not expose
internal planning artifacts as separate user-facing modules when they repeat
the same people, concepts, tools, or actions.

## Practical-action requirement

For an action-oriented request, include the actual setup and first-session
workflow. Name relevant software, platforms, equipment, accounts, templates,
or official portals. Separate:

- setup;
- what to do in the first session;
- decision rules;
- safety or quality checks;
- common failure modes.

If the user has an urgent deadline, create a minimum viable action path first,
then a slower learning path. Do not replace the requested action with
simulation, theory, or caution alone unless a concrete safety, legal, access,
or feasibility constraint makes that necessary.

## Resource-fit requirement

Treat format and cadence as part of resource quality. Determine or infer:

- typical session length;
- preferred formats;
- desired depth;
- language and region;
- budget and access;
- whether the user learns best through watching, reading, listening, doing, or
  a mixture.

When preference is unknown and would materially change the result, ask one
compact question with useful defaults. When time already reveals the likely
fit, infer it: a user with 15–30 minute sessions generally needs short videos,
concise articles, newsletters, podcasts, or small exercises before long books
or courses.

Offer a small number of distinct resource tracks when useful, such as:

- quick / short-session;
- balanced;
- deep / reference.

Each track must specify who it is for, its cadence, the exact resource order,
and what to consume from each resource. Do not recommend every media type by
default. Select the types that fit the topic and user, while giving at least
one alternative track when preferences are uncertain.

## Information-density test

Keep a sentence or block only if it does at least one of these:

- changes a decision;
- supplies verified evidence;
- names and differentiates a concrete option;
- gives an exact action;
- explains a material trade-off, limitation, or risk;
- defines a completion check.

Delete generic encouragement, repeated context, textbook throat-clearing,
obvious definitions, and disclaimers that do not change behavior. Use tables,
ranked lists, and compact cards when they make comparison faster.

## Presentation budget

Use five flexible top-level sections:

1. confirmed brief;
2. core guide;
3. curated resources;
4. roadmap;
5. source directory.

Put topic-specific structure into concise guide subsections rather than adding
top-level chapters. Put the immediate next action inside the core guide or
roadmap, not in a one-item top-level section.

The source directory is the final section. Group links by the channels the
user recognizes, such as official institutions, books, YouTube, Bilibili,
podcasts, repositories, newsletters, or communities. Every resource assigned
in a resource track or roadmap must remain a clickable link in both Markdown
and HTML.
